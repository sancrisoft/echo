# Glossary

Canonical terms for the Echo project. Docs and specs use these meanings; where code disagrees, the entry says so.

- **speaker bleed** — Teammate audio played through the loudspeakers re-entering the microphone and getting transcribed on the You channel. This is the phenomenon SP-001 addresses; docs prefer "speaker bleed" over "echo" because *Echo* is the app's name.
- **far-end reference** — The read-only copy of the captured system audio that the canceller treats as "what the speakers are playing." Standard AEC vocabulary; the counterpart of near-end.
- **near-end** — The raw microphone signal (user voice plus any speaker bleed) fed to the canceller.
- **double-talk** — The user and teammate audio speaking simultaneously. The hardest case for cancellation and deduplication, and a named acceptance scenario in SP-001.
- **output route** — The classification of the current audio output device (built-in speakers, headphones, or unsupported/ambiguous) that drives the echo-handling mode. Distinct from the raw Core Audio device.
- **echo-handling mode** — One of Cancelling, Bypassed, DedupOnly, or Degraded — the state the recording session is in with respect to speaker bleed (SP-001 state diagram).
- **convergence** — The initial adaptation period after the canceller starts or resets (e.g. on a device change) during which residual bleed can still pass. Success criteria allow a convergence grace.
- **Speaker** — In code, the `Speaker` enum means *who is talking*: `.me` (the user) or `.teammates`. Persisted as a plain string (`"me"` / `"teammates"`) with tolerant decoding of the older object encoding (SP-007, ADR-023). When referring to hardware, docs must say "loudspeaker" or "built-in speakers," never bare "speaker."
- **channel** — In code, `AudioChannel` means the *capture source* of a transcript segment: `.microphone` or `.system`. Distinct from Speaker (who talks); the channel→speaker mapping is the app's core attribution premise.
- **speech gates** — The absolute energy/shape thresholds (hard floor RMS 0.004 / peak 0.020, then per-channel speech-structure checks) that a chunk must pass before it is sent to Whisper. Defined term-by-term in `GateTerm` (`GateDiagnostics.swift`); `TranscriptionPipeline.shouldTranscribe` delegates to the same evaluation, so gate and diagnostics cannot drift. Load-bearing anti-hallucination defense, calibrated on built-in-mic levels; distinct from the AEC. BRN-002's subject.
- **input health** — The recording-time classification of an input channel's usability (usable, sustained-gated-out, or unsupported combination) that drives the input-health notice. Observational by decision (ADR-006): it raises and clears notices but never switches the audio path. Distinct from echo-handling mode, which keys on output route.
- **silent dropout** — The failure signature where the UI shows live input activity while a channel's transcript stays empty, because every chunk is discarded before Whisper sees it. The bug class SP-002 exists to eliminate; its ban is the "no silent dropout" success criterion.
- **transcription parity** — Equivalence to the built-in-mic baseline on the same scripted utterances, within normal Whisper variance (the containment measure the SP-001 acceptance suite uses). SP-002's support bar for USB-class microphones — deliberately weaker than "identical output".
- **capture gap** — An interval during which mic capture delivered no samples (device-switch teardown, device loss, degraded session start). The controller measures it with a monotonic clock and declares it via `TranscriptionPipeline.noteCaptureGap`, which force-finalizes pre-gap audio and advances that channel's clock — keeping cross-channel skew inside SP-001's 100 ms budget. Any new code path that stops mic capture must open a gap episode, or clocks silently skew.
- **speech model** — The WhisperKit checkpoint Echo transcribes with **live**, and the model recording is gated on: **large-v3-turbo** (~626 MB, mixed-bit quantized) — not the full large-v3 the UI historically claimed (SP-005 corrects the display strings; entry reconciled 2026-07-30). Distinct from the summary model and from the **final-pass model**; in code it is "the Whisper model" and its readiness is tracked by `SpeechModelState`. SP-003's subject.
- **summary model** — The local MLX LLM (`SummaryModelManager` / `SummaryModelState`) that writes the meeting notes after a recording (and, on a future branch, answers questions in Ask/Q&A). A *role*, not a fixed model: code binds it to Gemma 4 12B (~8.9 GB) today; SP-004 migrates it to Qwen3.5 4B (~3 GB) and deletes the retired snapshot at first launch (ADR-011). Needed only *after* a recording, never to record: downloaded eagerly on first launch behind the speech model, but loaded into RAM only for active summary work and released after an idle timeout (ADR-008). Distinct from the speech model and the (branch-only) embeddings model. The "~8.3 GB" the code hard-codes for its size is wrong — the real 12B snapshot measures 8.93 GB, the same discrepancy behind ADR-007's progress overflow; SP-004 retires those constants along with the model.
- **recording readiness** — The precondition for entering the recording state: the speech model is *loaded and able to transcribe*, not merely present on disk (ADR-009). An absent, downloading, loading, or failed speech model is "not ready" and blocks recording with a message rather than a fake recording state. Note the code overloads "ready": `SpeechModelState.ready` means loaded/transcribing-capable, whereas `SummaryModelState.ready` means the snapshot is on disk (not in RAM); the docs use "recording readiness" in the loaded sense.
- **snapshot** — One model's complete set of files on disk (weights, configs, tokenizer artifacts) under the shared models root, fetched from the model host. "Complete" is defined by the repo's actual file manifest — never a hardcoded layout — and is answerable offline (ADR-012). `SummaryModelState.ready` means a verified-complete snapshot on disk, not weights in RAM (the "ready" overload noted under recording readiness).
- **final pass** — The post-meeting re-transcription of a meeting's retained audio that produces the final transcript; never runs during a recording, never concurrent with the summary model. SP-005's subject.
- **live transcript** — The transcript the live pipeline persists at stop; the floor a meeting can never fall below — a failed final pass leaves it standing untouched. Since SP-007 it is never user-visible during recording (the live pipeline runs invisibly); it surfaces only as the **draft transcript** after a terminal pass failure.
- **draft transcript** — The live-floor transcript shown honestly labeled ("Draft") after finalization converges to terminal failure (or was never armed). The only state where live-pipeline text is user-visible; carries a manual Retry while the meeting's retained audio is kept (SP-007, ADR-024).
- **utterance** — Consecutive same-speaker transcript segments merged into one readable paragraph with a time range, for the transcript view and the summary input. A derived view that preserves its constituent segment IDs; never persisted (SP-007, ADR-021).
- **backchannel** — A standalone short acknowledgment ("Mm-hmm," "Okay," "Ajá") that signals listening rather than content. Kept in the persisted transcript but filtered out of utterance flow and summary input (SP-007); the classification list is build-owned.
- **provenance** — The meta.json record of what produced a meeting's current transcript and notes: transcript source (final pass vs. live floor), the speech model and RAM tier that actually served, fallback-or-not, and the summary model. Display and diagnostics only, with exactly one sanctioned scheduling use — disambiguating pending vs. terminal draft in the launch scan (SP-007, ADR-022/ADR-024). Absent on pre-SP-007 meetings, rendering as "unknown," never an error.
- **final transcript** — The transcript a successful final pass writes atomically in the live one's place; what summaries and Q&A are grounded in.
- **retained audio** — The compressed per-channel copy of a meeting's pipeline-ingested audio (post-AEC, gap-faithful timeline), kept inside the meeting folder solely to run the final pass. Its presence marks pending finalization (disambiguated from the terminal draft by provenance since SP-007); deleted on pass success, with the meeting, on "Keep draft," or after a successful manual Retry — terminal failure keeps it for the Retry (ADR-024 amending ADR-013/016). DEBUG builds may keep it past success as a development fixture (SP-007).
- **final-pass model** — The optional higher-accuracy speech checkpoint the final pass uses on capable machines (full large-v3 ~947 MB quantized on 16 GB+). A *role*, not a fixed checkpoint; never gates recording — absent means the final pass falls back to the live speech model.
- **RAM tier** — The machine class, by physical unified memory, that selects the final-pass model (8 GB reuses the live model; 16 GB+ gets the full-decoder checkpoint). Never affects live transcription.
- **turn template** — The exact text scaffold (role markers, system and user turns, generation prompt) wrapped around a prompt before it reaches the summary model. Echo owns it in code, transcribed per-model from the target repo's documented chat format, deliberately not tokenizer-applied templating — hand-building keeps the system prompt's survival guaranteed and inspectable (ADR-010). Model-specific: swapping the summary model means transcribing a new template (SP-004 moves Gemma turns → ChatML).
